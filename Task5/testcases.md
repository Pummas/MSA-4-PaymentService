# Task 5. Набор интеграционных и E2E-тестов OrchestrPay

## Стратегия тестирования

Для проверки корректности Saga-оркестрации используются:

- **E2E-тесты**: проверяют полный путь от запроса клиента до финального статуса в БД (включая BPMN-процесс, оркестратор
  и доменные сервисы).
- **Интеграционные тесты**: проверяют взаимодействие конкретных сервисов, работу с инфраструктурой, идемпотентность и
  отказоустойчивость.

### 🛠️ Тестовая инфраструктура (Testcontainers)

Все интеграционные и E2E-тесты запускаются в изолированном окружении с использованием библиотеки **Testcontainers**. Это
позволяет поднимать реальные зависимости в Docker-контейнерах непосредственно во время выполнения тестов, обеспечивая
максимальную приближенность к production-среде и reproducibility (воспроизводимость).

В тестах используются следующие контейнеры:

- **PostgreSQL (Testcontainers)**: для проверки транзакций, хранения состояний Saga и проверки логов операций. Для
  каждого теста поднимается чистая схема БД с применением миграций (Flyway/Liquibase).
- **Redis (Testcontainers)**: для проверки кэширования результатов внешних проверок, хранения фрод-меток и проверки
  идемпотентности запросов.
- **Camunda (Testcontainers)**: для запуска BPMN-движка и проверки корректности развертывания и исполнения диаграммы
  процесса.
- **WireMock (в Docker или встроенный)**: для эмуляции внешних сервисов (FraudCheck API, AML, GeoRisk) и управления их
  ответами (ALLOW, DENY, таймауты, ошибки).

## Таблица тест-кейсов

| Название                                            | Тип            | Компоненты                                                           | Предусловия                                                                                                                                                                                                                      |
|:----------------------------------------------------|:---------------|:---------------------------------------------------------------------|:---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| **E2E-01: Успешный платеж (Happy Path)**            | E2E            | Orchestrator, Payment, FraudCheck, Notification, DB (Testcontainers) | Клиент имеет достаточный баланс. Внешний Fraud API (WireMock) возвращает `ALLOW`.                                                                                                                                                |
| **E2E-02: Отказ антифрода (DENY) с авто-возвратом** | E2E            | Orchestrator, Payment, FraudCheck, Notification, DB (Testcontainers) | Внешний Fraud API возвращает `DENY`. Деньги уже списаны (`DEBIT_ACCOUNT`).                                                                                                                                                       |
| **E2E-03: Ручная проверка (MANUAL_REVIEW) — Успех** | E2E            | Orchestrator, Payment, FraudCheck, Notification, Camunda             | Fraud API возвращает `MANUAL_REVIEW`. Эмуляция ответа оператора `ALLOW` в течение 20 минут.                                                                                                                                      |
| **E2E-04: Ручная проверка (MANUAL_REVIEW) — Отказ** | E2E            | Orchestrator, Payment, FraudCheck, Notification, Camunda             | Fraud API возвращает `MANUAL_REVIEW`. Эмуляция ответа оператора `DENY`. Проверка каскадного возврата.                                                                                                                            |
| **E2E-05: Cut-off timeout ручной проверки**         | E2E            | Orchestrator, Payment, Camunda Timer, DB                             | Fraud API возвращает `MANUAL_REVIEW`. Оператор не отвечает 20 минут. Система должна применить `ALLOW` по умолчанию. (В тестах таймер Camunda ускоряется).                                                                        |
| **INT-01: Идемпотентность (Повторный запрос)**      | Интеграционный | Orchestrator, Redis (Testcontainers), PostgreSQL                     | Отправка двух одинаковых запросов на оплату с одинаковым `idempotency_key`. Второй запрос должен вернуть результат первого без повторного списания.                                                                              |
| **INT-02: Отказ БД при холдировании (HOLD_FUNDS)**  | Интеграционный | Orchestrator, Payment, PostgreSQL                                    | Эмуляция сбоя БД (например, deadlock) на этапе `HOLD_FUNDS`. Проверка, что Saga откатывается без зависших денег.                                                                                                                 |
| **INT-03: Таймаут внешнего FraudCheck API**         | Интеграционный | Orchestrator, FraudCheck, WireMock                                   | WireMock задерживает ответ внешнего API на 6 секунд. Проверка срабатывания retry-механизма и логирования ошибки.                                                                                                                 |
| **INT-04: Сбой Notification Service**               | Интеграционный | Orchestrator, Notification, Outbox, DB                               | Сервис уведомлений недоступен. Платеж должен успешно завершиться, а уведомления — уйти в Outbox (или retry-очередь), не блокируя основной поток.                                                                                 |
| **INT-05: Сбой списания (DEBIT_ACCOUNT)**           | Интеграционный | Orchestrator, Payment, Camunda, DB                                   | Ошибка на стороне `Payment Service` при списании (HTTP 500). Проверка запуска компенсации `RELEASE_FUNDS` и `CANCEL_PAYMENT`.                                                                                                    |
| **INT-06: Сбой перевода после списания (Pivot)**    | Интеграционный | Orchestrator, Payment, Notification                                  | Ошибка при `TRANSFER_PAYMENT` (после `DEBIT_ACCOUNT`). Возврат через Saga невозможен. Проверка генерации алерта в Security и перевода платежа в статус `MANUAL_INTERVENTION`.                                                    |
| **INT-07: Развертывание и валидация BPMN-схемы**    | Интеграционный | Camunda (Testcontainers), Orchestrator                               | При старте тестов контейнер Camunda поднимается, и в него автоматически деплоится BPMN-файл. Тест проверяет, что процесс успешно развернулся (нет ошибок валидации) и ключевые узлы (Pivot, Таймеры) присутствуют в определении. |
